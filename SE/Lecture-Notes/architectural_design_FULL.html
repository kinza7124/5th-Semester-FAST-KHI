01

Architectural Design — Introduction

Architectural Design — The first stage in the software design process. It is concerned with understanding how a software system should be organized and designing the overall structure of that system. Output = an architectural model describing the system as a set of communicating components.
Critical Link: Design ↔ Requirements
  • Architectural design is the critical link between design and requirements engineering.
  • Identifies the main structural components and the relationships between them.
  • RE process overlaps with architectural design — it is impossible for specification to not include some design information.
  • RE must show an abstract system architecture showing association of sub-systems, which is then used to discuss/fine-tune requirements with stakeholders.
Two Levels of Abstraction
Architecture in the Small
  • Architecture of individual programs
  • How a single program is decomposed into components
  • Focuses on internal structure
Architecture in the Large
  • Architecture of complex enterprise systems
  • Includes other systems, programs, program components
  • Distributed over different computers, possibly different companies
3 Key Advantages of Explicit Architecture
  • Stakeholder Communication: High-level view as focus of discussion with stakeholders; useful for elaborating design.
  • System Analysis for NFRs: Enables analysis of whether system can meet non-functional requirements (performance, security, etc.).
  • Large-Scale Reuse: Same architecture can be reused for similar application types (e.g., all banking systems share a core architecture).
Architectural Representations
  • Often modeled as informal block diagrams (box-and-line diagrams).
  • Boxes = Components; Nested Boxes = Sub-components; Arrows = Data/Control flow.
  • Box-and-line diagrams are very abstract — they do not show: nature of component relationships, externally visible properties (fault tolerance, shared resources).
  • Still useful for stakeholder communication and project planning.
  • ADL (Architecture Description Language) like UML or ArchiMate — globally recognized but time-consuming and expensive.
  • UML designed for OOP — more implementation-oriented than abstract. Best practice: Informal box/UML diagrams for architecture design.
Agile & Architecture
  • In agile, designing overall system architecture is done at an early stage.
  • Refactoring code is easy — refactoring architecture is expensive (large number of components must change).
  • Architecture decisions are costly to reverse unlike code-level decisions.
RE & Design Process Overlap

Architectural Design Decisions

Architectural design is a creative process — there is no formulaic design process. It is a series of decisions, not a sequence of activities. Depends on system type, architect's background, experience, and requirements.

Architectural Patterns — Overview

Architectural Pattern — A way of representing, sharing and reusing knowledge about software systems. The fundamental idea is separation of concern and data independence — beneficial for incorporating only localized changes.
What Every Pattern Description Must Include
  • Pattern Name — Unique identifier
  • Brief Description — What it does
  • Graphical Model — Visual representation
  • Example — Relevant system where pattern has been used
  • When to Use — Context and applicability
  • Pros & Cons — Strengths and weaknesses

Central shared data store. All components interact via repository, not directly with each other.

Runtime distributed architecture. Clients request services from dedicated servers.

Sequential data transformation through discrete filters connected by pipes.

MVC — Model-View-Controller

MVC separates an application into 3 distinct parts to segregate data presentation from data logic. It is the most widely used architectural pattern for web applications.
MVC Architecture — Components & Flow
Web Example — "Get Cats" Request
  • User clicks "Get Cats" → Controller receives request
  • Controller queries Model: runs SELECT * FROM cats
  • Model returns data to Controller
  • Controller passes data to View: View renders <h1>Cats</h1>
  • On failure: View renders error page instead. Controller decides which View to use.
  • Key Insight: Multiple views can be attached to same model (e.g., table view, chart view, mobile view) — changes in model reflect in all views.
FieldDetail
NameMVC (Model-View-Controller)
DescriptionSeparates presentation and interaction from system data. Divides into 3 parts. Way to segregate data presentation from data logic.
ExampleWeb-based application systems (Django, Rails, Laravel, Spring MVC, ASP.NET)
When UsedMultiple ways to view/interact with same data; future requirements for interaction are unknown; data changes frequently
Advantages
  • Data can change independently of its representation
  • Adding/changing a View does not affect underlying Model
  • Supports multiple presentations of same data
  • Changes in one View reflected in all others
  • Clear separation of responsibilities
Disadvantages
  • Can involve additional code overhead
  • Increases code complexity
  • Controller can become bloated ("fat controller")

Layered Architecture

Organizes system functionality into a set of layers, each providing a set of services to the layer above it. Every layer relies on facilities and services provided by the layer immediately beneath it.
Generic Layered Architecture — 4 Layers
iLearn System Example — Layered Architecture
FieldDetail
NameLayered Architecture
DescriptionOrganizes system into separate layers; lowest-level layers represent core services used throughout
ExampleiLearn system; system for sharing copyright documents across libraries; OS (kernel→drivers→OS services→UI); TCP/IP protocol stack
When UsedBuilding new facilities on top of existing systems; development spread across multiple teams; multi-level security requirement needed
Advantages
  • Easy to embed NFRs like security top-down without disrupting whole system
  • Only adjacent layer affected when a layer is updated
  • Supports multi-platform — only machine-dependent layers need change
  • Module replacement/upgradation is easy
  • Allows replacement of entire layers (if interface maintained)
  • Redundant facilities in each layer increases dependability
  • Multiple teams can work independently on different layers
Disadvantages
  • Performance issue — request must traverse multiple layers (overhead)
  • Difficult to code; creating true independence is challenging
  • High-level layer may need to interact directly with lower-level layers
  • Number of layers may not be obvious
07

Repository Architecture

All data managed in a central repository / database accessible to all system components. Components interact only through the repository — not directly with each other. Best used when large volumes of data are shared. It is a static structure — doesn't change at runtime.
Two ways sub-systems can exchange data:
  1. Repository Model (Option 1): Shared data held in a central database accessible to all sub-systems. Most common when large amounts of data are shared.
  2. Peer-to-Peer (Option 2): Each sub-system maintains its own database and passes data explicitly to other sub-systems.
Repository Pattern — IDE Example
FieldDetail
NameRepository
DescriptionAll data managed in a central repository accessible to all components. Components interact only through the repository, not directly.
ExampleIDE (Integrated Development Environment), MIS (Management Information Systems), CASE tool environments, version control systems (Git)
When UsedLarge volumes of information to be stored long-term; data-driven systems where data inclusion triggers an action or tool; when components are independent and data model is well-defined
Advantages
  • Components are independent — don't need to know other components exist
  • Changes by one component propagate to all automatically
  • All data managed consistently (backups done at same time)
  • Easy to add/remove tools
Disadvantages
  • Repository is a single point of failure — problems affect the whole system
  • Distributing the repository across computers may be difficult
  • All components coupled to repository's data model

Client-Server Architecture

Runtime organization of distributed systems. A set of services mounted over associated servers; clients access services via servers over a network. Unlike Repository, it is a dynamic architecture that can change at runtime.
Film Library System — Client-Server Architecture
FieldDetail
NameClient-Server
DescriptionFunctionality organized into services; each service provided by a separate server; clients access servers to use services
ExampleWeb applications; email servers; film library system; banking systems; e-commerce platforms
When UsedData in shared database accessed from many locations; variable load on system (clients scale independently); distributed system needed
3 ComponentsServers (print, file, management, etc.) · Clients (instances of client programs running concurrently) · Network (internet protocols)
Advantages
  • Resource sharing across multiple clients
  • Independent servers — failure of one doesn't necessarily affect others
  • No single point of failure for overall system
  • Transparent system upgradation
  • Servers can be distributed across the network
Disadvantages
  • Each service is a single point of failure — susceptible to DoS attacks
  • Performance unpredictable — depends on network and system load
  • Management problems if servers owned by different organizations
  • No shared data model — different servers may use different data formats

Pipe and Filter Architecture

Functional transformations (filters) process inputs to produce outputs. Data flows (as in a pipe) from one component to the next. When transformations are sequential → Batch Sequential Model. Analogy: UNIX shell pipe (ls | grep .txt | sort).
Not suitable for interactive/GUI systems: Input data stream needs to be pre-processed. GUI systems have complex input streams (mouse clicks, keyboard events) that are difficult to convert into a sequential stream.
Pipe and Filter — Generic Structure
Invoice Processing System — Pipe & Filter Example
Compiler Architecture — Pipe & Filter View (with shared Repository)
FieldDetail
NamePipe and Filter
DescriptionEach processing component (filter) is discrete and carries out one type of data transformation; data flows between filters through pipes
ExampleInvoice processing system; Compiler (lexical→syntactic→semantic→codegen); CNN pipeline (Input→Conv→Pool→Dense→Output); UNIX shell pipes; payment processing systems; ETL pipelines
When UsedData processing applications (batch and transaction-based); embedded systems; limited user interaction; compilers; business transaction processing
NOT SuitableInteractive/GUI systems — complex input streams (mouse, keyboard) cannot be easily converted to sequential streams
Advantages
  • Easy to understand; supports transformation reuse
  • Workflow style matches many business processes
  • Easy evolution by adding new transformations
  • Can be implemented as sequential OR concurrent system
  • Simple to test individual filters in isolation
Disadvantages
  • Data format must be agreed upon between communicating transformations
  • Each transformation must parse input and unparse output → overhead
  • May be impossible to reuse functional transformations with incompatible data structures
  • Not suitable for interactive systems

Application Architectures

A Generic Application Architecture is an architecture for a type of software system that includes the principal characteristics of a class of systems. These can be customized for specific requirements.
Why Generic Architectures are Needed
  • Application systems are designed to meet an organizational need.
  • Many organizations have similar needs → similar systems → same generic architecture with customizations.
  • E.g., all phone companies need: connect/meter calls, manage network, issue bills.
  • Multiple phone companies use a generic architecture + add their own specifics.
  • Architect identifies which generic architecture pattern(s) suit the system's NFRs.
How Generic Architectures are Used
  • Starting point for architectural design — pre-defined architectural patterns specific to application types.
  • Check whether proposed architecture matches a known generic architecture → can it be reused?
  • Use as a checklist of functionality to validate architectural design.
Application TypeDescriptionExamples
Data ProcessingData-driven; process data in batches without explicit user interventionBilling systems, payroll, batch ETL
Transaction ProcessingData-centered; process user requests and update information in a system databaseBanking, e-commerce, booking systems, ATMs
Event ProcessingSystem actions depend on interpreting events from the environmentAlarm systems, sensor monitoring, word processing
Language ProcessingUsers' intentions specified in a formal language processed and interpreted by the systemCompilers, interpreters, command-line shells
Two most widely used generic application architectures: Transaction Processing Systems (banking, e-commerce, booking) and Language Processing Systems (compilers).

Transaction: A sequence of operations treated as an atomic operation to ensure consistency in case of failure. All operations must complete successfully before database changes are made permanent (COMMIT). If any operation fails → ROLLBACK.

  • Ensures database consistency

User Perspective

📝 Exam Questions & Model Answers

All likely exam questions with complete answers — cover these and you're prepared

Q 01
What is architectural design? Why is it considered the critical link between design and requirements engineering?
Answer
Architectural design is the first stage in the software design process, concerned with understanding how a software system should be organized and designing its overall structure. The output is an architectural model describing the system as a set of communicating components.

It is called the critical link because: (1) it identifies main structural components and relationships from requirements; (2) it is impossible for requirements specification to exclude design information — RE and architectural design overlap; (3) the abstract architecture produced during RE is used to discuss and fine-tune requirements with stakeholders before detailed design begins.
Q 02
State three advantages of explicit architectural design. Explain each briefly.
Answer
  • Stakeholder Communication: Architecture provides a high-level view of the system that can be used as a discussion point with stakeholders, helping them understand the system without delving into technical details.
  • System Analysis over NFRs: An explicit architecture allows the architect to analyze whether the system can meet non-functional requirements such as performance, security, and availability before implementation.
  • Large-Scale Reuse: The same architecture can be reused for similar types of applications (e.g., all banking systems share a core architectural structure), reducing design effort and risk.
Q 03
What is an architectural pattern? What must every pattern description include?
Answer
An architectural pattern is a way of representing, sharing and reusing knowledge about software systems. The fundamental idea behind patterns is separation of concern and data independence — allowing only localized changes.

Every pattern description must include: Pattern name · Brief description · Graphical model · Example of a relevant system where it has been used · When to use it · Pros and cons (strengths and weaknesses).
Q 04
Explain the MVC architectural pattern with a complete web application example and flow.
Answer
MVC (Model-View-Controller) divides an application into 3 parts to segregate data presentation from data logic:
  • Model: Handles data logic; interacts with the database; performs CRUD operations, authentication, validation. Never talks to View directly.
  • View: Handles data presentation; renders dynamically generated HTML; shows data returned by Model.
  • Controller: Acts as middleman between Model and View; handles request flow; never handles data logic itself.
Flow (Web Example — "Get Cats"):
User clicks button → Controller receives HTTP request → Controller asks Model to run SELECT * FROM cats → Model returns data → Controller passes to View → View renders HTML page → Response sent to browser.

Key Advantage: Multiple views can be attached to the same model (table, chart, mobile). Changes in data reflect in all views. Adding/changing a View does not affect the Model.
Q 05
Describe the Layered architectural pattern. What are its rules? What are pros and cons?
Answer
Layered architecture organizes system functionality into a set of layers. Typical 4-layer structure: User Interface → Auth/Authorization → Business Logic → OS/Database.

Rules: (1) Every layer relies only on the layer immediately beneath it — no layer jumping; (2) Lower layers NEVER call upper layers — only respond; (3) Requesting something means iterating down through multiple layers.

Pros: Easy to add security/NFRs top-down; only adjacent layer affected when updating; supports multi-platform (change only machine-dependent layers); easy module replacement; multiple teams work independently.
Cons: Performance issue (traverses multiple layers); difficult to maintain true independence; high-level layer may need to interact with lower layers directly.
Q 06
Explain the Repository pattern. How does it differ from client-server? What is a single point of failure?
Answer
In the Repository pattern, all data is managed in a central repository/database accessible to all components. Components do not interact directly — only through the repository. It is a static structure (does not change at runtime). Best used when large volumes of data are shared long-term.

Difference from Client-Server: Repository is static (structure fixed at design time); Client-Server is dynamic (runtime organization — clients and servers can come and go). In Client-Server, components call each other over a network; in Repository, all interaction goes through a central store.

Single Point of Failure: Repository itself is one — if it fails, the entire system fails. This is its primary disadvantage.
Q 07
Explain the Client-Server architecture pattern. Name its three components. What is a single point of failure in this context?
Answer
Client-Server is the runtime organization of distributed systems. A set of services are mounted on associated servers; clients access these services over a network.

Three Components:
  • Servers: Provide specific services (print server, file server, management server, etc.)
  • Clients: Instances of client programs running concurrently on different machines; access services via remote procedure invocation using request-reply protocols
  • Network: Distributed system architecture using internet protocols (HTTP, TCP/IP)
Single Point of Failure: Each individual service/server is a single point of failure — if the video server in a film library goes down, users can't access videos. The overall system isn't a single point of failure (other servers still work), but individual services are. This makes client-server vulnerable to DoS (Denial of Service) attacks.
Q 08
Explain Pipe and Filter architecture. When is it NOT suitable? Give two examples of its use.
Answer
In Pipe and Filter, each processing component (filter) is discrete and performs one type of data transformation. Data flows (pipe) from one filter to the next. Analogy: UNIX shell piping. When transformations are sequential, this is called a Batch Sequential Model.

NOT suitable for interactive/GUI systems because: GUI systems have complex input streams (mouse clicks, keyboard events, touch input) that are difficult to convert into a sequential stream that can be processed step by step.

Examples: (1) Compiler — Lexical Analysis → Syntactic Analysis → Semantic Analysis → Code Generation; (2) Invoice Processing — Read incoming → Validate → Get recipient → Send reminder → Generate report. Also: CNN pipeline, payment processing, ETL pipelines.
Q 09
Explain the 4+1 View Model. Name and describe each of the 5 views.
Answer
The 4+1 View Model (Krutchen, 1995) was proposed because it is impossible to show all perspectives in a single diagram. It proposes 4 basic views linked via use cases (+1):
  • Logical View: Shows key abstractions in the system as objects or object classes; relates system requirements to entities. Used for understanding requirements.
  • Process View: Shows how system interacts with interacting processes at run-time. Used for judging NFRs like performance and availability.
  • Development View: Shows breakdown of software assigned to development teams. Useful for project managers and developers for planning.
  • Physical View: Shows how hardware and software components are distributed across processors. Useful for system engineers during deployment.
  • Conceptual View (+1, Hofmeister et al. 2000): Abstract view of high-level requirements to identify product-line architecture for future reuse; helps decide which components could be reused across products.
Q 10
What is a transaction? Describe the complete structure of a transaction processing system.
Answer
Transaction (System view): A sequence of operations treated as an atomic operation to ensure database consistency in case of failure. All operations must complete successfully before changes are committed (COMMIT). On failure → ROLLBACK. This ensures ACID properties.
Transaction (User view): Any coherent sequence of operations satisfying a goal (e.g., "find all flights from Karachi to Dubai").

Structure of a Transaction Processing System:
I/O Processing ↔ Application Logic ↔ Transaction Manager ↔ Database
  • User makes an asynchronous request via I/O component
  • Request processed by application-specific logic (business rules)
  • Transaction created and passed to Transaction Manager
  • Transaction Manager ensures ACID; on success, commits and returns success message
  • Success message passed back to application logic, then to I/O output
Often implemented as multi-tier client-server: Web Server (top) → App Server (middle) → Database Server (bottom).
Q 11
Name and describe all components of a compiler (language processing system).
Answer
  • Lexical Analyzer: Converts the HLL input program into a sequence of tokens (identifiers, keywords, operators, literals).
  • Symbol Table: Holds information about the names of entities (variables, class names, object names, function names) used in the text being translated. Shared data structure.
  • Syntax Analyzer: Checks if syntax is correct based on the grammar; builds a parse/syntax tree.
  • Syntax Tree: Internal tree structure representing the compiling program; shared between phases via the repository.
  • Semantic Analyzer: Uses syntax tree + symbol table to validate semantic correctness — type checking, undeclared variables, type mismatches, etc.
  • Code Generator: Traverses the syntax tree and generates abstract machine code (bytecode, assembly, IR).
The compiler uses a hybrid Pipe & Filter + Repository architecture: filters for sequential processing + shared repository (symbol table + syntax tree) accessible by all phases.
Q 12
How does system architecture affect NFRs? Give specific strategies for all 5 NFRs: performance, security, safety, availability, and maintainability.
Answer
System architecture directly determines whether NFRs can be satisfied. Each NFR has specific architectural strategies:
  • Performance: Localize critical operations in few co-located components (avoid distributed communication overhead); use large-grain components; use multiple processors/concurrent execution for task scheduling.
  • Security: Use layered architecture with critical assets in inner (lower) layers; multi-tier architecture; redundant auth & authorization at multiple levels.
  • Safety: Localize safety-critical features in small number of sub-systems; include a separate shutdown/fail-safe system; keep safety logic isolated from non-safety logic.
  • Availability: Include redundant components; design for fault-tolerant architecture; enable component replacement/update without system shutdown (hot-swappable components).
  • Maintainability: Use fine-grained (small, self-contained) components; avoid shared data structures (static variables, nesting); ensure loose coupling between components.
Conflict: Performance requires fewer, larger components; Maintainability requires more, smaller components. Resolution: Compromise on less critical requirement, or use multiple architectural styles for different subsystems.
Q 13
Differentiate between "architecture in the small" and "architecture in the large".
Answer
  • Architecture in the Small: Concerned with the architecture of individual programs. Depicts how a single program is decomposed into its constituent components, modules, and their relationships. Focus is on internal structure of one program.
  • Architecture in the Large: Concerned with the architecture of complex enterprise systems that include other complete systems, programs, and program components. These enterprise systems are distributed over different computers, which may be owned and managed by different companies. Focus is on system-of-systems interactions.
Q 14
What is a Generic Application Architecture? What are the 4 types of application systems?
Answer
A Generic Application Architecture is an architecture for a type of software system that includes the principal characteristics of a class of systems. Multiple organizations with similar needs use the same generic architecture with their own customizations added on top.

4 Types of Application Systems:
  • Data Processing Systems: Data-driven; process data in batches without explicit user intervention. (e.g., payroll, billing, ETL)
  • Transaction Processing Systems: Data-centered; process user requests and update information in a database. Most common type of interactive business systems. (e.g., banking, e-commerce, ATMs, booking)
  • Event Processing Systems: System actions depend on interpreting events from the environment. (e.g., alarm systems, sensor-based monitoring, word processors)
  • Language Processing Systems: Users' intentions specified in a formal language that is processed and interpreted by the system. (e.g., compilers, interpreters, command-line shells)
Q 15
Describe the Information System Architecture layers and how they map to servers in a distributed/multi-tier implementation.
Answer
4 Layers of Information System Architecture:
  • Layer 1 — User Interface: Presentation to user via web browser, desktop app, or mobile app.
  • Layer 2 — User Communications + Authentication & Authorization: Passes user queries, checks validations, session management, role-based access control.
  • Layer 3 — Information Retrieval & Modification: Application logic for accessing and updating data in the database; business rules processing.
  • Layer 4 — Transaction Management + System Database: Ensures ACID properties, COMMIT/ROLLBACK, persistent data storage.
Multi-Tier Client-Server Mapping:
  • Layers 1 → Web Server (handles UI delivery)
  • Layers 2+3 → Application Server (handles communications, auth, business logic)
  • Layer 4 → Database Server (handles transaction management and data storage)
Q 16
Why is refactoring architecture expensive compared to refactoring code? What does this mean for agile development?
Answer
Refactoring architecture is expensive because a large number of components must be changed to accommodate architectural changes. Architectural changes have cascading effects throughout the system — interfaces, data flows, and component interactions all need updating. Code refactoring (within a single component) is much simpler and localized.

For agile development, this means that even though agile emphasizes flexibility and iterative development, it is generally accepted that designing the overall system architecture should be done at an early stage. Architectural decisions are costly to reverse, unlike code-level decisions which can be changed during refactoring sprints. Agile approaches typically "architect a little, build a little" but the core architectural skeleton is established early.

Q 18
What architectural patterns would you use for: (a) a banking system, (b) a compiler, (c) an IDE, (d) a video streaming platform?
Answer
  • (a) Banking System: Transaction Processing + Layered + Client-Server. Transaction processing for atomic operations; Layered for security (auth in inner layers); Client-Server for distributed access from branches/ATMs/online.
  • (b) Compiler: Pipe and Filter + Repository (Hybrid). Pipe & Filter for sequential phases (lexical → syntactic → semantic → code gen); Repository for shared data (symbol table, syntax tree) between phases.
  • (c) IDE (Integrated Development Environment): Repository. Central repository stores AST, symbol table, grammar — all tools (editor, compiler, debugger, pretty-printer) read/write to it independently.
  • (d) Video Streaming Platform: Client-Server + MVC. Client-Server for distributed server infrastructure (video server, catalogue server, auth server); MVC for web application presentation.
