// 01 — Foundations

Introduction to Software Testing

What testing is, why it matters, and the core vocabulary.

💡

Definition: Software testing is the process of evaluating a program to detect anomalies, defects, crashes, incorrect computations, and data corruption — using sample input data.

🎯
VALIDATION

Validation Testing

Are we building the right product? Tests verify the system meets user requirements. A successful test confirms the software operates as intended.

🐛
DEFECT

Defect Testing

Are we building the product right? Tests deliberately try to make the system fail to expose bugs and incorrect behaviour.

⬛
BLACK-BOX

Black-Box Testing

Test the system from the outside — without looking at internal code. Only inputs and outputs are considered. Also called functional testing.

⬜
WHITE-BOX

White-Box Testing

Test with full knowledge of internal code structure. Each component (function, branch, path) is tested individually. Also called structural testing.

⚙️
FUNCTIONAL

Functional Testing

Verifying that each feature of the software works according to its specification. Does the login actually log you in?

📈
NON-FUNCTIONAL

Non-Functional Testing

Testing performance, scalability, reliability, security, usability — not specific features but system qualities and characteristics.

Input-Output Model of Testing

Every test follows this pattern: Test inputs → System under test → Observed outputs compared against Expected outputs. If output matches expected → validation test passed. If system behaves incorrectly → defect exposed.

// 02 — Verification & Validation

V&V and Inspections

Verification (Are we building it RIGHT?)
  • Static analysis of code
  • Code reviews & walkthroughs
  • Formal proofs
  • Checking conformance to spec
  • Does not run the code
Validation (Are we building the RIGHT product?)
  • Dynamic testing — runs the code
  • Meets user requirements?
  • Acceptance testing
  • System testing
  • User testing / UAT

Software Inspections (Static V&V)

Inspections involve people examining source representations (code, design, requirements) without executing the program. They can find defects before implementation completes and can be applied to any artifact.

✅ Advantages of Inspections

  • Error propagation impossible — errors don't hide other errors
  • Can inspect incomplete systems — no test harness needed
  • Check compliance with standards & coding style
  • More cost-effective for defect discovery than testing alone

❌ Limitations of Inspections

  • Cannot detect interaction-based defects (nothing runs)
  • Can't check non-functional properties (performance, usability)
  • Requires experienced reviewers
  • Time-intensive for large codebases
✅

Key point for exams: Inspections and testing are complementary, not competing. Use both. Inspections = static. Testing = dynamic.

V&V Confidence Factors

The level of V&V confidence needed depends on:

1

Software Criticality

A fire alarm system needs much higher confidence than a blog CMS. Safety-critical = maximum testing required.

2

User Expectations

New software gets some tolerance for bugs. Mature deployed software must be highly reliable.

3

Marketing Environment

Sometimes time-to-market matters more than zero defects (beta releases, MVPs).

Unit Testing in Detail

Unit testing tests individual components in isolation. It is a defect-testing process. Units may be individual functions, object classes with attributes and methods, or composite components.

Automated Test Structure (3 Parts)

1. Setup — Initialize system state, provide inputs and expected outputs.
2. Call — Execute the unit/method being tested.
3. Assertion — Compare actual result to expected. True = pass, False = fail.

Object Class Testing Checklist

When testing a class, ensure complete coverage:

📋 What to Test in a Class

  • All operations (methods) of the class
  • All attributes are set/read correctly
  • All events that change state (state machine transitions)
  • Inherited methods in subclasses — implementation may differ

🔄 State Transition Example

For a WeatherStation class, test the state chain:

Shutdown → Running → Shutdown

Some methods must be called in sequence — e.g., you must restart() before testing shutdown().

// 04 — Test Design Strategies

Equivalence Partitioning & Boundary Testing

Instead of testing every single input (impossible), group inputs into equivalence classes — inputs that should all be handled the same way. Test one value from each class, plus the boundaries.

Equivalence Partitioning Rule

If a program accepts inputs 4–10 integers, each being a 5-digit integer > 10,000, then your equivalence classes are: too few inputs, valid range, too many inputs, values < 10,000, valid values, non-integer values.

Whittaker's General Testing Guidelines

🛑 Force Error Messages

Design inputs that cause every possible error message to appear. Confirms error handling works.

💥 Buffer Overflow

Design inputs that overflow input buffers. Classic security and stability test.

🔁 Repeat Inputs

Repeat the same input multiple times. Checks for memory leaks and consistency issues.

⚠️ Force Invalid Outputs

Try to force the system to produce outputs that it should never generate (impossible states).

📏 Computation Limits

Force results to be too large or too small — find where the computation breaks down.

📦 Array Edge Cases

Test arrays of different sizes. Access first, middle, last elements. Test length of -1 (empty/null).

// 05 — White-Box Technique

Basis Path Testing & Cyclomatic Complexity

📐

Basis Path Testing is a white-box technique that ensures every independent execution path through a program is tested at least once. Based on graph theory — uses Control Flow Graphs (CFG).

Steps in Basis Path Testing

1

Label Nodes in Source Code

Assign numbers to each sequential block of statements and decision points in the code.

2

Create a Control Flow Graph (CFG)

Draw the graph: Nodes = blocks, Edges = flow between blocks. Each condition (if/loop) creates branching edges.

3

Calculate Cyclomatic Complexity (CC)

CC = E – N + 2P, where E = edges, N = nodes, P = connected components (usually 1). CC = number of independent paths.

4

Identify Independent Paths

List all basis paths. The count equals the Cyclomatic Complexity. Each path must traverse at least one new edge.

5

Create Test Cases for Each Path

Design inputs that force execution along each identified path, and note expected outputs.

Cyclomatic Complexity Formula

CC = E – N + 2P

E = Number of edges in CFG
N = Number of nodes in CFG
P = Number of connected components (usually = 1)

Shortcut: CC = Number of decision points (if, while, for, case) + 1
Interpretation: CC = minimum number of test cases needed for full branch coverage.

Worked Example — Triangle Classification

Java — Basis Path Example
// Step 1: Label each decision/block
public String classifyTriangle(int a, int b, int c) {
  // Node 1
  if (a + b <= c || b + c <= a || a + c <= b) {   // Edge → Node 2
    return "Not a triangle";                         // Node 2
  }
  // Node 3
  else if (a == b && b == c) {                      // Edge → Node 4
    return "Equilateral";                           // Node 4
  }
  // Node 5
  else if (a == b || b == c || a == c) {            // Edge → Node 6
    return "Isosceles";                             // Node 6
  }
  // Node 7
  else {
    return "Scalene";                               // Node 8
  }
}
// CC = 3 decisions + 1 = 4 → 4 independent paths

// 06 — Integration

Component & Interface Testing

Component testing checks that composite components (made of several interacting objects) behave correctly according to the component interface specification. Assumes unit testing of each individual part is already done.

Types of Component Interfaces

📦

Parameter Interfaces

Data is passed from one method/procedure to another via parameters. Most common. Tests: wrong order, wrong type, null values.

🧠

Shared Memory Interfaces

Block of memory shared between components. Common in embedded systems (sensor writes, analyser reads). Tests: timing, stale data, race conditions.

📞

Procedural Interfaces

A subsystem encapsulates procedures called by other subsystems. Like an API within a program. Tests: incorrect calls, wrong assumptions about behaviour.

✉️

Message Passing Interfaces

Subsystems request services from others (e.g., client-server, MPI). Tests: message format, timing, lost messages, ordering.

Types of Interface Errors

Interface Misuse

Calling component uses another component's interface incorrectly — e.g., parameters in wrong order. Detected by careful parameter checking.

Interface Misunderstanding

Calling component makes wrong assumptions about the called component's behaviour — e.g., calling a binary search with an unsorted array.

Timing Errors

Components operating at different speeds — one reads shared memory before the other has written the latest value. Real-time system hazard.

⚠️

Fault Propagation: In interface testing, a wrong value in Component A causes an error in Component B. The bug appears in B but the root cause is in A. This is why interface errors are hard to detect.

Interface Testing Guidelines

1

Extreme Parameter Values

Pass parameters at the extreme ends of valid ranges — check for overflow, underflow, null handling.

2

Design Failure-Causing Tests

Deliberately design tests to make components fail — expose assumptions that will break in production.

3

Stress Test Message Passing

In concurrent systems, use stress testing to expose timing errors — flood the system with messages.

// 07 — Development Methodology

Test-Driven Development (TDD)

🔄

TDD: Write the test first, then write the code that makes the test pass. The test defines what the code should do before you write it.

The TDD Cycle — Red → Green → Refactor

1

🔴 RED — Write a failing test

Write a test for the next small feature. Run it — it MUST fail because the feature doesn't exist yet.

2

🟢 GREEN — Write minimal code to pass

Write the simplest possible code to make the test pass. Don't over-engineer yet.

3

🔵 REFACTOR — Clean up the code

Improve code structure, remove duplication. Run all tests again to ensure nothing broke.

4

↩️ REPEAT

Move to the next small increment of functionality and repeat the cycle.

Benefits of TDD

🎯

100% Code Coverage

Every line of code you write has at least one test. Defects discovered immediately when introduced.

🔁

Regression Testing Built-In

Run the full test suite after every change. New code that breaks existing functionality is caught immediately.

🐞

Simplified Debugging

When a test fails, the newly-written code is the culprit. No need for complex debugging — the failure scope is tiny.

📄

Living Documentation

Tests describe exactly what each function should do. Better documentation than comments because it's always up-to-date.

Regression Testing

Regression Testing

Re-running all existing tests after a code change to verify that previously working functionality hasn't been broken. With automation, this happens on every commit. TDD dramatically reduces the cost of regression testing.

// 08 — Final Stages

Release & User Testing

Release Testing
  • Testing a specific release for external use
  • Performed by a separate testing team
  • Black-box — tests derived from specification
  • Goal: validate the system is good enough for release
  • Includes requirements-based and performance tests
System Testing
  • Tests the full integrated system
  • Performed by development team + QA
  • Focus: finding bugs (defect testing)
  • Checks component interactions
  • Part of development process

Requirements-Based Testing

For every requirement, create one or more test cases that verify it is met. This is validation testing — confirming the system does what it promised.

Dvago Pharmacy Case Study

Req 1: Customer searches medicine availability → Test: search "Panadol", expect found/not-found result.
Req 2: If available, upload prescription before adding to cart → Test: add without prescription, expect error. Add with valid prescription, expect success.
Req 3: Stock reduces after order → Test: order 5 units, verify stock decremented by 5.
Req 4: Sold-out message if unavailable → Test: search out-of-stock item, expect "sold out" message.

Types of User Testing

🅰️

Alpha Testing

Users work directly with the development team at the developer's site. Provides early interface design feedback. Controlled environment.

🅱️

Beta Testing

Software released to a limited group of early adopters in their own environment. They report issues back. No developer present.

✅

Acceptance Testing (UAT)

Customer formally tests the system to decide if it's ready for deployment. A formal sign-off process. Customer can accept or reject.

Acceptance Testing Process

1

Define Acceptance Criteria

Clarify uncertain requirements. Document what "done" looks like. Part of the system contract.

2

Plan Acceptance Testing

Allocate resources, time, budget. Define risks and mitigation strategies.

3

Derive Acceptance Tests

Cover all functional AND non-functional requirements. Complete requirement coverage.

4

Run Tests in Real Environment

Execute agreed tests in the customer's actual working environment — not a test lab.

5

Negotiate Results

Rarely is everything perfect. Developer and customer negotiate what's acceptable, what needs fixing.

6

Accept or Reject System

Customer formally decides: accept as-is, accept with conditions, or reject and require revision.

// 09 — Non-Functional

Performance & Stress Testing

📊

Performance Testing

Test system under expected load conditions. Increase load steadily until performance becomes unacceptable. Identifies performance bottlenecks.

💥

Stress Testing

Deliberately overload the system beyond its designed capacity. Identifies the breaking point and confirms fail-soft behaviour (graceful degradation, no data loss).

⚡

Load Testing

Simulate expected production load. Verify the system handles peak traffic without degradation. E.g., 300 concurrent users for an e-commerce site.

🌐

Distributed System Stress

Most useful for identifying defects in distributed environments. System degradation begins as soon as threshold is exceeded. Find that point.

Basic Unit Tests

JavaScript — math.js + math.test.js
// math.js — the code we're testing
function add(a, b) { return a + b; }
function divide(a, b) {
  if (b === 0) throw new Error('Cannot divide by zero');
  return a / b;
}
module.exports = { add, divide };

// ─────────────────────────────────────────────
// math.test.js — the test file
const { add, divide } = require('./math');

describe('Math functions', () => {

  // ─── Positive Tests ───
  test('adds two positive numbers', () => {
    expect(add(2, 3)).toBe(5);
  });

  test('adds negative numbers', () => {
    expect(add(-2, -3)).toBe(-5);
  });

  // ─── Boundary Tests ───
  test('adds zero to a number', () => {
    expect(add(5, 0)).toBe(5);
  });

  // ─── Error / Negative Tests ───
  test('throws on divide by zero', () => {
    expect(() => divide(10, 0)).toThrow('Cannot divide by zero');
  });

  test('divides correctly', () => {
    expect(divide(10, 2)).toBe(5);
  });
});

Async / API Testing

JavaScript — API Tests with Mock
// api.js — fetches user data
const axios = require('axios');
async function getUser(id) {
  const response = await axios.get(`https://api.example.com/users/${id}`);
  return response.data;
}

// api.test.js
const axios = require('axios');
const { getUser } = require('./api');

// Mock axios so we don't hit real API
jest.mock('axios');

describe('getUser', () => {
  test('returns user data on success', async () => {
    const mockUser = { id: 1, name: 'Alice' };
    axios.get.mockResolvedValue({ data: mockUser });

    const user = await getUser(1);
    expect(user).toEqual(mockUser);
    expect(axios.get).toHaveBeenCalledWith(
      'https://api.example.com/users/1'
    );
  });

  test('throws error when API fails', async () => {
    axios.get.mockRejectedValue(new Error('Network Error'));
    await expect(getUser(1)).rejects.toThrow('Network Error');
  });
});

Basic Pytest Structure

Python — bank.py + test_bank.py
# bank.py — code under test
class BankAccount:
    def __init__(self, balance=0):
        self.balance = balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("Deposit amount must be positive")
        self.balance += amount

    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("Insufficient funds")
        self.balance -= amount

    def get_balance(self):
        return self.balance

# ─────────────────────────────────────────────
# test_bank.py — test file (must start with test_)
import pytest
from bank import BankAccount

# ─── Fixture: reusable setup ───
@pytest.fixture
def account():
    """Creates a fresh BankAccount for each test"""
    return BankAccount(balance=100)

# ─── Positive Tests ───
def test_deposit_increases_balance(account):
    account.deposit(50)
    assert account.get_balance() == 150

def test_withdraw_decreases_balance(account):
    account.withdraw(30)
    assert account.get_balance() == 70

# ─── Negative Tests ───
def test_withdraw_raises_on_insufficient_funds(account):
    with pytest.raises(ValueError, match="Insufficient funds"):
        account.withdraw(200)

def test_deposit_raises_on_negative_amount(account):
    with pytest.raises(ValueError):
        account.deposit(-10)

# ─── Boundary Tests ───
def test_deposit_zero_raises(account):
    with pytest.raises(ValueError):
        account.deposit(0)

def test_withdraw_entire_balance(account):
    account.withdraw(100)
    assert account.get_balance() == 0

Parametrize — Data-Driven Testing

Python — Parametrize (Equivalence Partitioning)
import pytest

def classify_age(age):
    if age < 0: raise ValueError("Age cannot be negative")
    if age < 13: return "child"
    if age < 18: return "teenager"
    if age < 65: return "adult"
    return "senior"

# Parametrize: run same test with many inputs at once
@pytest.mark.parametrize("age, expected", [
    (0,  "child"),      # boundary: min
    (5,  "child"),      # middle of class
    (12, "child"),      # boundary: max child
    (13, "teenager"),   # boundary: min teenager
    (17, "teenager"),   # boundary: max teenager
    (18, "adult"),      # boundary: min adult
    (64, "adult"),      # boundary: max adult
    (65, "senior"),     # boundary: min senior
    (100, "senior"),    # large valid
])
def test_classify_age(age, expected):
    assert classify_age(age) == expected

@pytest.mark.parametrize("age", [-1, -100])
def test_negative_age_raises(age):
    with pytest.raises(ValueError):
        classify_age(age)

Mocking with pytest-mock

Python — Mock External Dependencies
# pip install pytest-mock
import requests
from unittest.mock import patch, MagicMock

def fetch_user(user_id):
    response = requests.get(f"https://api.example.com/users/{user_id}")
    if response.status_code == 200:
        return response.json()
    return None

# Mock the requests.get call
@patch('requests.get')
def test_fetch_user_success(mock_get):
    mock_response = MagicMock()
    mock_response.status_code = 200
    mock_response.json.return_value = {"id": 1, "name": "Alice"}
    mock_get.return_value = mock_response

    result = fetch_user(1)
    assert result == {"id": 1, "name": "Alice"}
    mock_get.assert_called_once_with("https://api.example.com/users/1")

@patch('requests.get')
def test_fetch_user_not_found(mock_get):
    mock_response = MagicMock()
    mock_response.status_code = 404
    mock_get.return_value = mock_response

    result = fetch_user(999)
    assert result is None

Selenium Web Automation

🤖

Selenium automates browser interactions for end-to-end testing. It simulates a real user clicking, typing, and navigating — used for UI regression testing and acceptance testing.

Python — Selenium Login Test
from selenium import webdriver
from selenium.webdriver.common.by import By
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC
import pytest

@pytest.fixture
def driver():
    d = webdriver.Chrome()          # or Firefox(), Edge()
    d.implicitly_wait(10)
    yield d
    d.quit()                         # cleanup after each test

def test_valid_login(driver):
    driver.get("https://example.com/login")

    # Find elements and interact
    driver.find_element(By.ID, "email").send_keys("user@test.com")
    driver.find_element(By.ID, "password").send_keys("Secret123!")
    driver.find_element(By.CSS_SELECTOR, "button[type='submit']").click()

    # Wait for dashboard to load and verify
    wait = WebDriverWait(driver, 10)
    welcome = wait.until(
        EC.presence_of_element_located((By.CLASS_NAME, "welcome-message"))
    )
    assert "Welcome" in welcome.text

def test_invalid_login(driver):
    driver.get("https://example.com/login")
    driver.find_element(By.ID, "email").send_keys("wrong@email.com")
    driver.find_element(By.ID, "password").send_keys("wrongpass")
    driver.find_element(By.CSS_SELECTOR, "button[type='submit']").click()

    error = driver.find_element(By.CLASS_NAME, "error-message")
    assert "Invalid credentials" in error.text

  • Human tester executes tests step by step
  • Good for exploratory, ad-hoc, UX testing
  • No coding skills required
  • Slow, expensive for regression
  • Use for: new features, one-time tests
Automated Testing
  • Scripts run tests automatically
  • Fast regression, CI/CD integration
  • Requires programming skills
  • High initial setup cost, low long-term cost
  • Use for: regression, performance, repetitive tasks

Top Interview Questions & Answers

🎯

Interview Tip: Always link theory to practice. When asked about testing types, mention which tools you'd use. When asked about test cases, write them out on paper/whiteboard clearly.

Core Concepts

What is the difference between verification and validation?
Verification: "Are we building the product right?" — static checking that code conforms to specification (code reviews, static analysis, inspections). Does not run code.

Validation: "Are we building the right product?" — dynamic testing that the system meets user requirements. Runs the actual code.

Mnemonic: Verification = spec correct. Validation = user happy.
What is the difference between black-box and white-box testing?
Black-box: Test without knowing internal code. Only inputs and outputs matter. Basis: specification/requirements. Example: testing a login form without seeing server code.

White-box: Test with full knowledge of internal code. Design tests for branches, paths, loops. Example: basis path testing, code coverage analysis.

Grey-box: Partial knowledge. Common in integration testing.
Explain TDD and why it's valuable. Write a TDD example.
TDD = Write test FIRST, then write code to pass it. Cycle: Red → Green → Refactor.

Benefits: 100% code coverage, built-in regression testing, tests serve as documentation, simplified debugging (failing test pinpoints the problem).

Example:
// Step 1: Write failing test
test('isPalindrome("racecar") returns true', () => {
  expect(isPalindrome("racecar")).toBe(true); // FAILS — fn doesn't exist
});

// Step 2: Write minimal code
function isPalindrome(s) { return s === s.split('').reverse().join(''); }

// Step 3: Test passes. Refactor if needed.
What is Cyclomatic Complexity and how do you calculate it?
Cyclomatic Complexity (CC) measures the logical complexity of code — the number of independent paths through it.

Formula: CC = E – N + 2P (Edges – Nodes + 2 × Connected Components)
Shortcut: CC = Number of decision points + 1

Example: A function with 3 if-statements has CC = 4 → needs minimum 4 test cases for full path coverage.

Interpretation: CC ≤ 10 = simple, 11–20 = moderate, >20 = complex (refactor recommended).
What is Equivalence Partitioning? Give a practical example.
EP divides inputs into groups (partitions) where all values in a group should behave the same way. You test one value from each partition instead of every value.

Example — Age input for a system accepting 1–120:
• Invalid partition 1: < 1 (e.g., 0, -5) → expect error
• Valid partition: 1–120 (e.g., 25) → expect success
• Invalid partition 2: > 120 (e.g., 150) → expect error
• Invalid type: "abc" → expect error

Add Boundary Testing: test 0, 1, 120, 121 — boundaries are where most bugs hide.
What's the difference between alpha, beta, and acceptance testing?
Alpha Testing: Users test at the developer's site with developer support. Early, controlled, focused on interface usability. Done before beta.

Beta Testing: Software released to a limited group of external users in their own environment. Developer not present. Users report bugs.

Acceptance Testing (UAT): Customer formally tests the system to decide if it should be deployed. Results in an official accept/reject decision.

Order: Development → System Testing → Alpha → Beta → UAT → Production
Write test cases for a calculator's divide function.
TC-001: 10 ÷ 2 = 5 (positive / positive)
TC-002: -10 ÷ 2 = -5 (negative / positive)
TC-003: 0 ÷ 5 = 0 (zero numerator)
TC-004: 10 ÷ 0 → Error: "Division by zero" (zero denominator)
TC-005: 0 ÷ 0 → Error (both zero)
TC-006: 1 ÷ 3 = 0.333... (float result)
TC-007: MAX_INT ÷ 1 = MAX_INT (overflow check)
TC-008: "abc" ÷ 2 → Type Error (string input)
TC-009: null ÷ 2 → Error (null input)
What is regression testing and when do you run it?
Regression testing = re-running all existing tests after a code change to ensure nothing previously working has been broken.

When to run:
• After every bug fix (verify fix didn't break something else)
• After adding a new feature
• After code refactoring
• Before every release
• Automatically on every commit in CI/CD pipelines

Tools: Jest (--watch mode), pytest, Selenium suites in Jenkins/GitHub Actions.
What is mocking in testing? Why is it important?
Mocking replaces real dependencies (APIs, databases, external services) with fake, controlled versions during testing.

Why:
• Tests run in isolation — no real network calls
• Tests are fast and deterministic
• Can test error scenarios (API down, 404, timeout) easily
• No cost or side effects from hitting real services

In Jest: jest.mock('axios'), then axios.get.mockResolvedValue({...})
In Python: @patch('requests.get') decorator or unittest.mock.MagicMock()
Explain stress testing vs load testing vs performance testing.
Performance Testing: Broad term for testing system speed, scalability, and stability under load.

Load Testing: Test with expected peak load. E.g., simulate 1000 concurrent users on an e-commerce site during Black Friday.

Stress Testing: Push beyond the limit until the system breaks. Goal: find the breaking point, confirm graceful degradation (no data loss, good error messages).

Spike Testing: Sudden, extreme increase in load — then back to normal. Tests elasticity.

Soak Testing: Run at normal load for a long time — find memory leaks.
What's the testing pyramid? How do you apply it?
The Testing Pyramid (Mike Cohn) describes the ideal distribution of test types:

🔺 Top (few): E2E / UI Tests — Selenium, Cypress. Slow, expensive, brittle. Test critical user journeys only.
🔷 Middle: Integration Tests — Test multiple components together. APIs, databases, services interacting.
🔲 Bottom (many): Unit Tests — Fast, cheap, isolated. The foundation. Aim for >70% coverage here.

Rule of thumb: 70% Unit, 20% Integration, 10% E2E. Avoid the "ice cream cone" anti-pattern (inverted pyramid — mostly manual/E2E).
