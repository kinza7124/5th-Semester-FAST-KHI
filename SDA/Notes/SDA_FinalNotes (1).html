1. Design Patterns

1.1 Purpose of Design Patterns

Definition: A design pattern is a general, reusable solution to a commonly occurring problem within a given context in software design. It is not a finished design that can be transformed directly into code but rather a template or description for how to solve a problem.

Why Do We Need Design Patterns?

Design patterns serve as proven solutions that experienced developers have used to solve recurring problems. They provide a shared vocabulary for developers, making it easier to communicate complex design concepts. The key purposes include:

  1. Reusability: Patterns provide tested, proven development paradigms that can be reused across multiple projects, reducing development time and effort.
  2. Common Vocabulary: They establish a standard terminology that all developers understand, facilitating better team communication.
  3. Best Practices: Patterns capture best practices that have evolved over time, helping developers avoid common pitfalls.
  4. Abstraction: They provide a higher level of abstraction, allowing developers to think about the solution rather than low-level implementation details.
  5. Maintainability: Well-applied patterns make code more maintainable and easier to understand for future developers.
  6. Flexibility: Patterns often promote loose coupling and high cohesion, making systems more flexible and adaptable to change.
Design patterns are NOT algorithms. An algorithm solves a computational problem, while a design pattern solves a design problem. Be prepared to distinguish between these in MCQs.

1.2 Categories of Design Patterns (Gang of Four)

The Gang of Four (GoF) - Erich Gamma, Richard Helm, Ralph Johnson, and John Vlissides - categorized 23 classic design patterns into three main categories:

Category Purpose Patterns
Creational Deal with object creation mechanisms, trying to create objects in a manner suitable to the situation Singleton, Factory Method, Abstract Factory, Builder, Prototype
Structural Deal with object composition, forming larger structures from individual objects and classes Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy
Behavioral Deal with object collaboration and responsibility distribution among objects Chain of Responsibility, Command, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor

1.3 Detailed Study of Common Design Patterns

1.3.1 Singleton Pattern (Creational)

Intent: Ensure a class has only one instance and provide a global point of access to it.

Structure:

Singleton Pattern Structure
Legend: - (minus) = private member | + (plus) = public member | Underlined = static member

When to Use:

  • When exactly one instance of a class is needed (e.g., database connection pool, logger, configuration manager)
  • When the single instance should be extensible by subclassing
  • When clients should be able to use an extended instance without modifying their code

Advantages:

  • Controlled access to sole instance
  • Reduced namespace pollution (avoids global variables)
  • Permits refinement of operations and representation
  • Permits a variable number of instances (can be modified)

Disadvantages:

  • Difficult to unit test due to global state
  • Violates Single Responsibility Principle (handles own creation)
  • Can mask bad design (hiding dependencies)
  • Thread-safety issues in multi-threaded environments
A common exam question asks about thread-safe Singleton implementation. Remember: use double-checked locking, synchronized method, or static inner class approach.

1.3.2 Factory Method Pattern (Creational)

Intent: Define an interface for creating an object, but let subclasses decide which class to instantiate. Factory Method lets a class defer instantiation to subclasses.
Factory Method Pattern Structure
Legend: Dashed border = Interface | Solid border = Class | Hollow arrow = Inheritance | Dashed line with arrow = Dependency

When to Use:

  • When a class can't anticipate the class of objects it must create
  • When a class wants its subclasses to specify the objects it creates
  • When you want to localize the knowledge of which helper class is the delegate

Advantages:

  • Eliminates the need to bind application-specific classes into the code
  • Provides hooks for subclasses (more flexible than direct object creation)
  • Connects parallel class hierarchies

Disadvantages:

  • May lead to many subclasses just to implement the factory method
  • Clients might have to subclass the Creator class just to create a particular ConcreteProduct

1.3.3 Observer Pattern (Behavioral)

Intent: Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically.
Observer Pattern Structure
Legend: * = many (multiplicity) | Hollow arrow = Implements | Solid arrow = Association | Dashed arrow = Dependency

Real-World Example: News subscription service where multiple subscribers receive updates when new articles are published.

When to Use:

  • When a change to one object requires changing others, and you don't know how many objects need to change
  • When an object should be able to notify other objects without making assumptions about who these objects are
  • Implementation of event handling systems

Advantages:

  • Abstract coupling between Subject and Observer
  • Support for broadcast communication
  • Supports the Open/Closed Principle

Disadvantages:

  • Unexpected updates (observers don't know about each other)
  • Memory leaks if observers are not properly detached
  • Order of notification is not guaranteed

1.3.4 Strategy Pattern (Behavioral)

Intent: Define a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently from clients that use it.
Strategy Pattern Structure
Legend: Dashed border = Interface | Hollow arrow = Implements | Solid arrow = Has-a (Composition)

When to Use:

  • When many related classes differ only in their behavior
  • When you need different variants of an algorithm
  • When an algorithm uses data that clients shouldn't know about
  • When a class defines many behaviors as conditional statements
Strategy pattern is often confused with State pattern. Key difference: In Strategy, the client chooses the strategy; in State, the context changes state internally based on conditions.

1.3.5 Decorator Pattern (Structural)

Intent: Attach additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality.
Decorator Pattern Structure
Legend: Hollow arrow = Inheritance/Implements | Solid curved arrow = Has-a relationship (wraps component)

Real-World Example: Coffee shop where you can add toppings (milk, sugar, whipped cream) to a base coffee, each adding to the cost and description.

Advantages:

  • More flexibility than static inheritance
  • Avoids feature-laden classes high up in the hierarchy
  • Follows Open/Closed Principle
  • Can add or remove responsibilities at runtime

Disadvantages:

  • Can result in many small objects
  • Can be confusing to understand the structure
  • Identity issues (a decorated component is not identical to the component itself)

1.3.6 Adapter Pattern (Structural)

Intent: Convert the interface of a class into another interface clients expect. Adapter lets classes work together that couldn't otherwise because of incompatible interfaces.
Adapter Pattern Structure (Object Adapter)
Legend: Client uses Target interface | Adapter implements Target and wraps Adaptee | Adaptee has incompatible interface

When to Use:

  • When you want to use an existing class but its interface doesn't match what you need
  • When you want to create a reusable class that cooperates with unrelated or unforeseen classes
  • When integrating legacy code with new systems

1.4 Homogenization of Classes

Homogenization refers to the process of making different classes conform to a common interface or structure, allowing them to be treated uniformly. This is a key principle in object-oriented design that enables polymorphism and loose coupling.

Key Concepts:

  • Interface Standardization: Different classes implement the same interface, allowing clients to interact with them uniformly without knowing their concrete types.
  • Abstraction Layer: Creating abstract base classes or interfaces that define common behavior expected from all conforming classes.
  • Polymorphic Behavior: Enables treating objects of different classes through a common interface, supporting runtime binding.

Benefits:

  • Reduces coupling between components
  • Increases code reusability
  • Simplifies client code (works with abstractions, not implementations)
  • Supports the Dependency Inversion Principle
Homogenization is closely related to the Liskov Substitution Principle (LSP) - objects of a superclass should be replaceable with objects of subclasses without affecting program correctness.

2. UML Diagrams

Introduction to UML

Unified Modeling Language (UML) is a standardized general-purpose modeling language in software engineering. It provides a set of graphic notation techniques to create visual models of object-oriented software systems.

UML diagrams are divided into two main categories:

  1. Structural Diagrams: Depict the static structure of a system (Class, Component, Deployment, Object diagrams)
  2. Behavioral Diagrams: Depict the dynamic behavior of a system (Use Case, Activity, State, Sequence, Collaboration diagrams)

2.1 State Diagram (State Machine Diagram)

Purpose: A State Diagram describes the states an object can be in during its lifetime and the events/transitions that cause state changes. It models the dynamic behavior of a single object in response to a series of events.

Key Elements:

  • State: A condition during the life of an object (represented by rounded rectangle)
  • Initial State: Starting point (filled black circle)
  • Final State: Ending point (filled circle within a circle - "bull's eye")
  • Transition: Movement from one state to another, triggered by an event
  • Guard Condition: Boolean condition [in brackets] that must be true for transition
  • Action: Activity performed during transition (after /)
ATM Transaction System: An ATM machine goes through various states from being idle, to authenticating the user, processing transactions, and finally returning to idle.
State Diagram: ATM Transaction System

How to Draw in Exam:

  1. Identify all possible states of the object
  2. Draw initial state (filled circle) at the starting point
  3. Draw each state as a rounded rectangle with state name
  4. Add internal activities (entry/, do/, exit/) where applicable
  5. Draw transitions as arrows between states with event labels
  6. Add guard conditions [in brackets] on transitions
  7. Draw final state(s) where the object lifecycle ends
In exams, always label transitions clearly with events. Remember: entry/ runs when entering state, do/ runs while in state, exit/ runs when leaving state.

2.2 Deployment Diagram

Purpose: A Deployment Diagram shows the physical architecture of a system, depicting how software artifacts are deployed on hardware nodes.

Key Elements:

  • Node: A physical computing resource (3D box) - servers, workstations, devices
  • Artifact: A physical piece of software deployed on a node (rectangle with «artifact»)
  • Communication Path: Connection between nodes showing network/communication
  • Device: A physical machine (stereotyped as «device»)
  • Execution Environment: Software environment needed to run artifacts
Online Shopping System: A typical e-commerce platform with web servers, application servers, database servers, and client browsers.
Deployment Diagram: Online Shopping System

How to Draw in Exam:

  1. Identify all hardware nodes (servers, devices, external systems)
  2. Draw nodes as 3D boxes with appropriate stereotypes
  3. Place artifacts inside nodes showing what software runs where
  4. Draw communication paths between nodes
  5. Label paths with protocol/connection type (HTTP, TCP/IP, etc.)
Deployment diagrams frequently appear in exams for enterprise application questions. Always show the physical separation between client, server, and database tiers.

2.3 Collaboration Diagram (Communication Diagram)

Purpose: A Collaboration Diagram shows how objects interact to perform a specific task, emphasizing the structural organization of objects and the messages passed between them. Unlike sequence diagrams, it focuses on object relationships rather than time ordering.

Key Elements:

  • Object: An instance of a class (rectangle with underlined name: objectName:ClassName)
  • Link: Connection between objects showing relationship (solid line)
  • Message: Communication between objects, numbered to show order
  • Sequence Number: Indicates the order of message execution (1, 1.1, 1.2, 2, etc.)
University Course Registration System: A student registers for a course through the portal. The system validates prerequisites and confirms enrollment.
Collaboration Diagram: Course Registration

Message Numbering Scheme:

  • Sequential (1, 2, 3...): Messages at the same level
  • Nested (1.1, 1.2, 2.1...): Messages triggered as part of processing another message
  • Concurrent (1a, 1b): Messages happening in parallel (asynchronous)
Collaboration diagrams are equivalent to Sequence diagrams in information but differ in emphasis. Collaboration shows object structure; Sequence shows time ordering.

2.4 Timing Diagram

Purpose: A Timing Diagram shows behavior of objects over a specific time period. It focuses on timing constraints and how states change along a timeline, making it ideal for real-time and embedded systems.

Key Elements:

  • Lifeline: Horizontal line representing an object over time
  • State/Condition Timeline: Shows different states an object goes through
  • Time Axis: Horizontal axis showing progression of time
  • State Changes: Vertical transitions between states
  • Duration Constraint: Time duration for a state {min..max}
  • Message: Arrow showing communication between lifelines
Traffic Light System: A traffic light cycles through Red, Yellow, and Green states with specific timing constraints for each phase.
Timing Diagram: Traffic Light Controller

How to Draw in Exam:

  1. Draw horizontal time axis at the bottom
  2. List objects/lifelines vertically on the left
  3. Draw state lines horizontally for each state duration
  4. Show state changes as vertical lines
  5. Add duration constraints in curly braces
  6. Add timing marks on the time axis
Timing diagrams are essential for real-time systems. Focus on duration constraints and state transitions when answering questions about embedded or time-critical systems.

2.5 Activity Diagram

Purpose: An Activity Diagram describes the workflow or business process of a system. It shows the sequence of activities, decision points, parallel activities, and synchronization, similar to a flowchart but with support for concurrent behavior.

Key Elements:

  • Activity: A task or action (rounded rectangle)
  • Initial Node: Starting point (filled circle)
  • Final Node: Ending point (circle with inner filled circle)
  • Decision Node: Branch point with conditions (diamond)
  • Merge Node: Combines alternative flows (diamond)
  • Fork: Splits flow into parallel activities (thick bar)
  • Join: Synchronizes parallel activities (thick bar)
  • Swimlane: Partition showing responsibility (vertical/horizontal lane)
Hospital Patient Admission System: When a patient arrives, they go through registration, triage, examination, and either treatment or admission based on severity.
Activity Diagram: Hospital Patient Admission

How to Draw in Exam:

  1. Identify swimlanes (actors/departments responsible)
  2. Start with initial node (filled circle)
  3. Draw activities as rounded rectangles
  4. Use diamonds for decision/merge nodes with conditions
  5. Use thick bars for fork/join (parallel activities)
  6. End with final node
  7. Connect with arrows showing flow direction
Activity diagrams are frequently asked for business process modeling. Always use swimlanes when multiple actors are involved. Label decision branches with guard conditions.

2.6 Class Diagram

Purpose: A Class Diagram is the most important structural diagram showing the static structure of a system by depicting classes, their attributes, methods, and relationships between classes.

Key Elements:

  • Class: Rectangle divided into three compartments (name, attributes, methods)
  • Visibility: + (public), - (private), # (protected), ~ (package)
  • Attributes: visibility name: type [= default value]
  • Methods: visibility name(parameters): returnType
  • Abstract Class/Method: Written in italics or with «abstract»
  • Interface: Marked with «interface» stereotype
Online Shopping System: An e-commerce application with customers, orders, products, and payment processing.
Class Diagram: Online Shopping System

2.7 UML Relationships (Very Important)

Relationship Symbol Description Example
Association Solid line General relationship between classes. Objects of one class use/interact with objects of another. Student enrolls in Course
Aggregation Hollow diamond → Weak "has-a" relationship. Part can exist independently of the whole (shared ownership). Department has Professors (professors can exist without department)
Composition Filled diamond → Strong "has-a" relationship. Part cannot exist without the whole (exclusive ownership). If whole is deleted, parts are deleted. Order has OrderItems (items don't exist without order)
Inheritance Hollow arrow → "Is-a" relationship. Subclass inherits from superclass. Arrow points to parent. Car extends Vehicle
Dependency Dashed arrow → Weaker relationship where one class temporarily uses another (method parameter, local variable). Order uses PaymentProcessor
Realization Dashed hollow arrow → Class implements an interface. Shows contract implementation. CreditCardPayment implements Payment
Key Difference: Aggregation vs Composition
• Aggregation (hollow diamond): Parts can survive without the whole. Example: Team and Players (players exist without team).
• Composition (filled diamond): Parts cannot survive without the whole. Example: House and Rooms (rooms are destroyed with house).

2.8 Boundary, Control, and Entity Classes (BCE Pattern)

The BCE pattern (also called Robustness Diagram or ECB) is an analysis pattern that categorizes classes based on their responsibilities in the system architecture.
Class Type Symbol Responsibility Examples
Boundary Circle with vertical line on left Interface between system and external actors. Handles input/output. UI screens, API endpoints, hardware interfaces. LoginScreen, PaymentForm, PrinterInterface
Control Circle with arrow Business logic and coordination. Controls the flow between boundary and entity classes. Contains use case logic. LoginController, OrderProcessor, PaymentHandler
Entity Circle with underline Data and business rules. Persistent objects representing domain concepts. Usually maps to database tables. Customer, Order, Product, Account
BCE Pattern: Login Use Case
BCE is essential for Robustness Diagrams. Remember: Actors only interact with Boundary classes. Boundary talks to Control. Control coordinates with Entity. Entity stores data.

2.9 Use Case Diagram

Purpose: A Use Case Diagram captures the functional requirements of a system, showing actors (users/external systems) and the use cases (functionality) they can perform. It defines the system boundary.

Key Elements:

  • Actor: External entity interacting with the system (stick figure)
  • Use Case: A piece of functionality (oval/ellipse)
  • System Boundary: Rectangle enclosing use cases
  • Association: Line connecting actor to use case
  • Include: Mandatory inclusion of another use case «include»
  • Extend: Optional extension of functionality «extend»
  • Generalization: Inheritance between actors or use cases
University Portal System: Students, professors, and administrators interact with the system for registration, grading, and course management.
Use Case Diagram: University Portal

Asynchronous Communication in Use Cases:

In some scenarios, use cases involve asynchronous communication where the actor doesn't wait for an immediate response:

  • Notification patterns: System sends email/SMS after completing an action
  • Background processing: Long-running tasks like report generation
  • Event-driven interactions: System reacts to events (sensor triggers, time-based jobs)
  • Represented with notes or stereotypes like «async» on the association
«include» means the base use case ALWAYS includes the included use case. «extend» means the extension SOMETIMES happens based on a condition. Arrow direction: include arrow points TO included; extend arrow points TO base.

3. Software Process Models

3.1 Introduction to Process Models

A Software Process Model (also called Software Development Life Cycle - SDLC) is a structured approach defining the phases, activities, and deliverables in software development. It provides a roadmap from initial requirements to final deployment and maintenance.

3.2 Waterfall Model

The Waterfall Model is a linear, sequential approach where each phase must be completed before the next begins. Progress flows downward like a waterfall through phases.

Phases:

  1. Requirements Analysis: Gather and document all requirements
  2. System Design: Create architecture and design specifications
  3. Implementation: Write code based on design
  4. Testing: Verify the system works correctly
  5. Deployment: Release to production
  6. Maintenance: Fix bugs and add enhancements
Waterfall Model

Advantages:

  • Simple and easy to understand and manage
  • Well-documented process with clear milestones
  • Works well for small projects with clear requirements
  • Phases don't overlap, reducing confusion

Disadvantages:

  • No flexibility to go back to previous phases
  • Late discovery of problems (testing is late)
  • Not suitable for complex or long projects
  • Customer sees product only at the end
  • High risk of failure if requirements change

When to Use: Small projects, well-understood requirements, stable technology, fixed-price contracts.

3.3 Incremental Model

The Incremental Model delivers the product in small, usable increments. Each increment adds functionality to the previous version, building up the complete system over time.
Incremental Model

Advantages:

  • Working software delivered early
  • Easier to test and debug smaller increments
  • Customer can provide feedback on early versions
  • Lower initial cost; funds can be allocated per increment

Disadvantages:

  • Requires good planning and design from start
  • Total cost may be higher than waterfall
  • Integration issues between increments possible

When to Use: When core features are well-understood but additional features can evolve, large systems that can be divided into parts.

3.4 Spiral Model

The Spiral Model combines iterative development with systematic risk management. Each loop of the spiral represents a phase, with risk analysis at each iteration.

Four Quadrants (per iteration):

  1. Planning: Determine objectives, alternatives, constraints
  2. Risk Analysis: Identify and resolve risks
  3. Engineering: Develop and verify the product
  4. Evaluation: Customer evaluation and planning next iteration
Spiral Model

Advantages:

  • Strong emphasis on risk management
  • Good for large, complex, high-risk projects
  • Flexible; requirements can evolve
  • Customer involvement at each iteration

Disadvantages:

  • Complex and requires expertise in risk assessment
  • Expensive due to multiple iterations
  • Not suitable for small projects
  • Success depends on risk analysis accuracy

When to Use: Large-scale, high-risk, mission-critical systems (aerospace, military, healthcare).

3.5 Agile Model

Agile is an iterative and incremental approach emphasizing flexibility, customer collaboration, and rapid delivery of working software. It values individuals, working software, customer collaboration, and responding to change.

Agile Manifesto Values:

  • Individuals and interactions over processes and tools
  • Working software over comprehensive documentation
  • Customer collaboration over contract negotiation
  • Responding to change over following a plan

Common Agile Frameworks:

  • Scrum: Sprints (2-4 weeks), daily standups, product backlog, sprint reviews
  • Kanban: Visual workflow, WIP limits, continuous delivery
  • XP (Extreme Programming): Pair programming, TDD, continuous integration
Agile/Scrum Process

Advantages:

  • Highly adaptive to changing requirements
  • Continuous customer involvement and feedback
  • Early and frequent delivery of working software
  • Team collaboration and self-organization
  • Reduced risk through short iterations

Disadvantages:

  • Less predictable scope, timeline, and budget
  • Requires experienced and committed team
  • Documentation may be insufficient
  • Customer must be available and engaged
  • Difficult for fixed-price contracts

When to Use: Uncertain or evolving requirements, need for fast delivery, small to medium teams, customer can be closely involved.

3.6 Process Model Comparison (Exam Reference)

When asked "which model to use", consider: (1) Are requirements clear and stable? (2) Is risk high? (3) How involved can the customer be? (4) What's the project size and timeline?

4. The 4+1 View Model

4.1 Introduction

The 4+1 View Model, introduced by Philippe Kruchten, is an architectural framework that describes software architecture using five concurrent views. Each view addresses specific concerns of different stakeholders (end users, developers, system integrators, project managers).

The model is called "4+1" because it consists of 4 views plus the Use Case View (Scenarios) that ties them all together:

  1. Logical View - The functionality
  2. Process View - The concurrency
  3. Development View - The implementation
  4. Physical View - The deployment
  5. Use Case View - The scenarios (+1)
4+1 View Model Architecture

4.2 Logical View

The Logical View describes the functionality that the system provides to end-users. It focuses on the object model of the design, showing how the system is decomposed into objects or classes.

Key Aspects:

  • Stakeholders: End users, domain experts, business analysts
  • Concerns: Functionality, features, domain concepts
  • UML Diagrams: Class diagrams, Object diagrams, State diagrams
  • Elements: Classes, interfaces, packages, relationships

Example Application:

For an e-commerce system, the Logical View would show classes like Customer, Product, Order, ShoppingCart, and their relationships, representing the domain model that supports the shopping experience.

4.3 Process View

The Process View addresses the dynamic aspects of the system, explaining the system's processes and how they communicate. It focuses on runtime behavior, concurrency, synchronization, and performance.

Key Aspects:

  • Stakeholders: System integrators, performance engineers
  • Concerns: Concurrency, distribution, performance, scalability, fault tolerance
  • UML Diagrams: Activity diagrams, Sequence diagrams, Communication diagrams
  • Elements: Processes, threads, tasks, interactions

Example Application:

For an e-commerce system, the Process View would show how web request handling processes work, how background tasks process orders, and how different services communicate asynchronously.

4.4 Development View

The Development View (also called Implementation View) describes the static organization of the software in its development environment. It shows how the software is decomposed for development purposes.

Key Aspects:

  • Stakeholders: Programmers, software managers, build engineers
  • Concerns: Software module organization, team structure, reuse, build management
  • UML Diagrams: Component diagrams, Package diagrams
  • Elements: Modules, components, packages, layers, libraries

Example Application:

For an e-commerce system, the Development View would show the package structure (com.shop.cart, com.shop.payment), component dependencies, and how modules are organized for different development teams.

4.5 Physical View

The Physical View (also called Deployment View) describes the mapping of software onto hardware and the physical architecture. It shows how the software elements are distributed across the infrastructure.

Key Aspects:

  • Stakeholders: System engineers, deployment engineers, DevOps
  • Concerns: Hardware topology, installation, network configuration, scalability
  • UML Diagrams: Deployment diagrams
  • Elements: Nodes, devices, connections, artifacts

Example Application:

For an e-commerce system, the Physical View would show web servers, application servers, database servers, load balancers, and how they are connected in the network topology.

4.6 Use Case View (Scenarios - The +1)

The Use Case View captures the key scenarios that drive the architecture. It serves as both validation and illustration for other views, showing how the architecture realizes important use cases.

Key Aspects:

  • Stakeholders: All stakeholders (common ground)
  • Concerns: Understanding requirements, validating architecture
  • UML Diagrams: Use Case diagrams, Sequence diagrams for scenarios
  • Purpose: Ties other views together, drives and validates architecture

Why "+1"?

The Use Case View is special because it's not a standalone architectural view but rather a validation mechanism. Key scenarios are used to test if the architecture supports the required functionality. Each scenario walks through multiple views.

4.7 How Views Relate in Real Systems

View Answers Diagrams Real System Example
Logical What does the system do? Class, Object Domain classes: Order, Product, Customer
Process How does it execute at runtime? Activity, Sequence Order processing thread, async payment handler
Development How is code organized? Component, Package com.shop.web, com.shop.service, com.shop.data
Physical Where does it run? Deployment AWS EC2, RDS, Load Balancer configuration
Use Case What are key scenarios? Use Case, Sequence Checkout process, User registration
The 4+1 View Model is frequently asked in exams. Remember: Logical (WHAT), Process (HOW at runtime), Development (HOW organized for coding), Physical (WHERE deployed), Use Case (WHY - validates all).

5. System Architecture Views

5.1 Why Are Views Needed?

An Architectural View is a representation of a system's architecture that focuses on a particular set of concerns. No single view can capture all aspects of a complex system.

Reasons for Multiple Views:

  1. Complexity Management: Large systems are too complex to understand in a single representation. Views decompose complexity.
  2. Stakeholder Separation: Different stakeholders have different concerns. A developer cares about code structure; an operator cares about deployment.
  3. Separation of Concerns: Each view focuses on specific quality attributes (performance, security, modifiability).
  4. Communication: Views provide a common vocabulary for discussing architecture with specific audiences.
  5. Documentation: Complete architecture documentation requires multiple views to be comprehensive.

5.2 Common Architectural Views

5.2.1 Module View (Static Structure)

Shows the static code structure of the system. Elements are modules (classes, packages, layers). Relationships are "uses", "inherits", "belongs to".

  • Decomposition Style: Shows how system is divided into modules
  • Uses Style: Shows dependencies between modules
  • Layered Style: Shows organization into layers

5.2.2 Component-and-Connector View (Runtime)

Shows the runtime structure. Elements are components (processing units) and connectors (communication pathways). Shows how the system behaves when running.

  • Client-Server Style: Clients request services from servers
  • Pipe-and-Filter Style: Data flows through processing filters
  • Publish-Subscribe Style: Components publish events; subscribers react

5.2.3 Allocation View (Environment Mapping)

Shows how software elements are mapped to non-software elements in the environment.

  • Deployment Style: Software to hardware mapping
  • Work Assignment Style: Modules to development teams
  • Implementation Style: Modules to file/directory structure

5.3 Architectural Styles (Patterns)

An Architectural Style is a collection of design decisions that characterize a family of systems. Common styles include:

Style Description Advantages Use When
Layered System organized into horizontal layers, each providing services to the layer above Separation of concerns, maintainability, testability Enterprise applications, web apps (MVC)
Client-Server Clients request services from centralized servers Centralized data, easy maintenance Web applications, databases
Microservices Small, independent services with their own databases Scalability, independent deployment Large distributed systems, cloud-native
Event-Driven Components communicate through events Loose coupling, asynchronous processing Real-time systems, IoT, GUIs
Pipe-and-Filter Data flows through sequence of processing filters Reusability, parallel processing Data transformation, compilers, Unix commands
Repository Central data store accessed by multiple components Data consistency, centralized control IDEs, databases, CASE tools

5.4 Applying Views in Real-World Systems

Example: Hospital Management System

Module View:

Shows the static structure with packages:

  • com.hospital.patient - Patient registration, records
  • com.hospital.doctor - Doctor management, schedules
  • com.hospital.billing - Invoice generation, payments
  • com.hospital.inventory - Medicine, equipment tracking

Component-and-Connector View:

Shows runtime components:

  • Web Application (handles HTTP requests)
  • Appointment Scheduler Service (manages bookings)
  • Notification Service (sends SMS/email)
  • Database Connector (manages data persistence)

Allocation/Deployment View:

Shows hardware mapping:

  • Web Server (nginx) on Cloud VM
  • Application Server (Tomcat) on dedicated server cluster
  • Database Server (PostgreSQL) on managed cloud service
  • Redis Cache on memory-optimized instance

5.5 View Documentation Best Practices

Each View Document Should Include:

  1. Primary Presentation: The main diagram showing elements and relationships
  2. Element Catalog: Description of each element in the view
  3. Context Diagram: Shows how the system relates to its environment
  4. Variability Guide: Points of flexibility and configuration
  5. Rationale: Why architectural decisions were made
When documenting architecture: (1) Choose views based on stakeholders and their concerns, (2) Document each view consistently, (3) Show relationships between views, (4) Explain rationale for key decisions.

5.6 Exam Quick Reference: Views Summary

Concept Key Points
Why Multiple Views? Complexity management, stakeholder separation, separation of concerns
4+1 Views Logical, Process, Development, Physical + Use Cases (validation)
Module View Static code structure (classes, packages, layers)
C&C View Runtime structure (components, connectors, data flow)

Architectural Styles Layered, Client-Server, Microservices, Event-Driven, Pipe-Filter, Repository
Architecture is about making the right trade-offs. No single view or style is "best" – the right choice depends on quality attribute requirements (performance, security, modifiability, etc.) and project constraints.
